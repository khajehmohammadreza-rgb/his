# روال استاندارد توسعه و نگهداری

## ۱. مرجع واقعی را شناسایی کن

قبل از هر تغییر، نسخه نصب‌شده، بسته سورس متناظر، Commit مبنا، محیط PHP/Node و ساختار پایگاه داده ثبت شوند. **`main` این مخزن هنوز با آخرین نسخه عملیاتی HIS یکسان‌سازی نشده است.** فایل‌های Node قدیمی ریشه ممکن است به استقرار قبلی وابسته باشند؛ حذف/انتقال بدون ممیزی ممنوع است.

## ۲. شاخه و Pull Request

- شاخه `feature/<topic>` برای قابلیت، `fix/<topic>` برای اصلاح و `docs/<topic>` برای مستندات بساز.
- هر PR باید هدف، مسیرهای تغییر، ریسک، آزمون‌ها و روش Rollback را روشن کند.
- پیش از Merge، بررسی کد و نتیجه تست خودکار الزامی است. هیچ PR صرفاً به دلیل سبزبودن تست نحوی «آماده نصب روی بیمارستان» نیست.
- تغییرات مربوط به `apps/catalog`، `apps/his` و سورس میراثی `apps/kiosk` در یک PR ترکیب نشوند، مگر وابستگی آن مستند باشد.

## ۳. نسخه‌بندی و انتشار

- نسخه برنامه، Build، Commit، فایل نصب/ارتقا و SHA-256 باید به هم قابل ردیابی باشند.
- برچسب Release فقط برای خروجی آزموده‌شده با سورس معادل ساخته شود.
- انتشار آزمایشی از انتشار عملیاتی کاملاً جدا باشد.
- کلیدها، کد امضای باینری، اطلاعات بیمار و بکاپ در GitHub Actions artifact عمومی منتشر نشوند.

## ۴. بررسی پیش از استقرار

- بررسی نحوی PHP و JavaScript، تست‌های رگرسیون مرتبط و امنیت پیکربندی اجرا شوند.
- پایگاه داده واقعی کپی‌شده برای آزمون باید بی‌نام‌سازی شود؛ اطلاعات بیماران در مخزن یا log تست قرار نگیرد.
- سناریوهای ثبت بیمار، صندوق، تخفیف، بیمه، ترخیص، چاپ و بازگشت از خطا آزمایش شوند.
- Backup و Restore واقعی در محیط آزمایشی تأیید و سپس Deploy کنترل‌شده انجام شود.
- شکست هر مرحله یعنی توقف انتشار و Rollback مطابق مستندات.
